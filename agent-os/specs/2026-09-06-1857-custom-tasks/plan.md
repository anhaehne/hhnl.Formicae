# Issue #15: reusable custom agent tasks (0.15.0)

Status: implemented and independently reviewed with callback/output-race and worker-deadline amendments. Local verification completed for 0.15.0; deployment verification follows the push. Acceptance requires defining/reusing a custom task, validating inputs before execution, and persisting outputs. This increment adds a generic agent task rather than aliasing Implement or Plan.

## Catalog and immutable version contract

Add a `CustomTaskDefinition` catalog with server-generated immutable string ID, Name, Description, PromptTemplate, input definitions, runner configuration, Revision, IsDeleted and timestamps. Use the Persona catalog's permission and optimistic-concurrency conventions: viewers list/inspect, management administrators create/update/delete, expectedRevision on updates/deletes, stale writes return 409, deleted IDs return 404, soft deletion preserves snapshots. Labels need not be unique.

The catalog has no mutable built-in entries. Existing four built-in task types remain directly selectable and unchanged. Add `builtins.custom-task` with `customTask: { taskId, inputs, snapshot? }`; custom task settings are forbidden on every other node type. Resolve each distinct task catalog ID once when creating a workflow version and replace all supplied snapshots with the current authoritative snapshot. Include ID/revision/name/description/template/input definitions/runner settings in that immutable snapshot. Node IDs, editor metadata, model selection and persona settings remain unchanged.

Enabled saves validate catalog references, input schema/template and node values before persisting. Disabled drafts retain unresolved IDs/values and field/node errors, omit unresolved snapshots, and snapshot resolvable definitions. Runtime validates only pinned snapshots and prepared task inputs, never rereads the task catalog. Existing saved versions remain executable after catalog edits/deletion; new saves deliberately capture current revisions and show that difference in the editor. A custom task without a valid pinned snapshot must fail rather than fall back to a built-in.

## Typed inputs and template language

Input definitions are an ordered list of at most 32 entries. Names match `[A-Za-z][A-Za-z0-9_]{0,63}` and are case-sensitive/unique. Each entry has `name`, `valueType: string|number|boolean`, `required`, and optional typed `defaultValue`. The name is its stable template identifier; display labels can be added later. Strings are limited to 16,000 characters, numeric values must fit invariant decimal exactly, have absolute value at most 9,007,199,254,740,991, and round-trip through a finite IEEE-754 double formatted with invariant shortest `R` spelling back to the same decimal. This matches the browser JSON number contract: ordinary fractions such as 0.1 and 1.25 remain valid; unsafe integers, precision-losing fractions and decimal underflow are rejected. Arbitrary-precision decimal input is not supported. Booleans are JSON booleans. Arrays, objects and explicit null node values are rejected. Required means presence, so an empty string is a valid string value. An absent value uses its typed default if defined; a required value without a default fails; an optional value without a default remains absent. Null/omitted defaultValue both mean no default, matching nullable JSON round trips. Reject undeclared node inputs and mismatched/default types. Bound the entire resolved input JSON to 65,536 UTF-8 bytes before saving/launching.

PromptTemplate is required, non-whitespace and at most 16,000 characters; Name is trimmed/nonempty/max120, Description max2,000. Use a small single-pass parser, not a template engine or expression evaluator. Exact permitted tokens:

- `{{input.NAME}}` for declared inputs.
- `{{workflow.issueUrl}}`, `{{workflow.repositoryUrl}}`, `{{workflow.baseBranch}}`, `{{workflow.model}}`, `{{workflow.planArtifact}}`, `{{workflow.pullRequestUrl}}` for the existing allowlisted workflow fields.

No whitespace inside tokens, nested tokens, dynamic property traversal, filters, functions, loops, partials, clock values, shell expansion or arbitrary expressions. Unknown tokens and unmatched double-brace delimiters fail catalog validation. Single braces remain literal text; literal double-brace sequences are not supported in templates initially. Input values are substituted exactly once and never reparsed as templates, so a value containing `{{workflow.model}}` stays literal. String values preserve their text; number/boolean values use invariant scalar JSON spelling. Absent optional inputs and missing optional workflow fields render as empty text, with absence retained in the structured audit/context JSON. This is an explicit rendering rule, not type coercion. Bound rendered prompt plus persona guidance to 131,072 UTF-8 bytes and fail before launch if exceeded. Reject a final composed prompt that is empty or whitespace before job creation (for example, a template containing only an absent optional input); do not defer this failure to WorkerEnvironment.Required.

Provide resolved input and referenced workflow-field values as a fixed-name `custom-task-inputs.json` context file. Do not derive filenames, commands or environment keys from input names or values. Inputs are ordinary operator-provided data, not secret references; per-step secrets remain #18.

## Runner configuration and execution authority

Runner configuration is deliberately small: `{ kind: "agent", timeoutSeconds: 1800 }`, with timeout between 1 and 3,600 seconds. Supply `RuntimeJobExecutionPolicy(timeoutSeconds, 0)` to both runtime adapters and add an independent worker deadline for Custom. That deadline must cancel and terminate the child process tree for both Codex and OpenHands when elapsed, even if the scheduler is unavailable. It must not depend on CanCommitRepositoryChanges or enter checkpoint/resume/commit logic; the existing commit-oriented WorkerDeadlinePolicy is unsuitable unchanged. Kubernetes activeDeadlineSeconds and local runtime timeout polling remain additional enforcement layers. No arbitrary command/entrypoint, image, environment variables, repository mode, tool list or credential settings are accepted. AI configuration/model remain existing per-step selections; persona inheritance now also applies to Custom AI tasks. The selected supported agent provider remains Codex/OpenHands as resolved by the existing AI settings service.

Custom tasks execute in the existing worker's fresh `/workspace` scratch directory with the prepared context file. They do **not** request repository checkout, repository access tokens, browser provisioning or nested-container runtime. They do not automatically commit/push, checkpoint changes, post issue comments, manipulate workflow labels, update PlanArtifact, or create pull requests. Codex and OpenHands must both receive the same scratch working directory explicitly; currently OpenHands receives no working-directory override when checkout is disabled, which must be corrected specifically for Custom execution.

This limits automatic Formicae behavior and supplied resources. It does not claim sandboxed filesystem/network isolation: the existing CLI can execute commands, and capability/environment enforcement remains future work. Custom prompt text is trusted management configuration and never grants additional platform permissions. Repository-aware modes, custom tools/images, scripts and per-step secrets are outside #15.

## Generic scheduler, persistence and retry

Append `TaskRunKind.Custom`, `WorkflowStep.Custom`, and `WorkflowStatus.Running` after existing enum members without changing their current ordinals. Existing EF mappings persist these as strings, so enum additions need no enum conversion migration. Update explicit type/status/retry/history mappings and frontend unions; do not route Custom through built-in planning/implementation label gates or direct PR handlers.

Add a dedicated generic agent-task orchestration path. Identify executions by DefinitionStepId and exact loop iteration. Before first launch persist a TaskRun with durable ExecutionAttemptId and an immutable `CustomTaskExecutionJson` containing custom task identity/revision/name, resolved typed inputs, referenced workflow-field values, runner timeout and the pre-persona rendered prompt. Capturing workflow values before launch makes retries deterministic when PlanArtifact or other workflow state later changes. Compose the pinned persona from that base prompt once for each launch; preserve existing model/AI inheritance. No catalog read occurs on run/retry.

Use the existing stable external job identity/reuse path. Transient launch uncertainty retains the same execution attempt and prepared snapshot for recovery; accepted jobs must not be duplicated after bookkeeping/logging failure. Explicit user retry creates a new attempt ID while preserving the prepared input snapshot and pinned catalog/persona revisions. For loop iterations, each new TaskRun captures fresh allowed workflow values; retries of that iteration reuse them. Ensure initial launch failure without an assigned external ID remains retryable. Do not hold an EF transaction across external launch calls.

In workflows containing Custom tasks, task retry is restricted to the current node and latest loop iteration, following the existing Decision workflow restriction. Workflow retry selects failures only at the current node; it must not reset an unrelated historical failed task while leaving the cursor elsewhere. Prepared state survives both retry endpoints.

Poll and persist completion through the generic task path. Success advances only the node's Next or its owning Loop Return; failure uses existing workflow failure handling without any built-in side effects. Empty successful output is valid. The output contract is plain text from the existing AgentRunResult extraction, not a new structured agent protocol. Persist the complete final text in TaskRun.Output up to 262,144 characters. If output exceeds that limit, persist a bounded diagnostic prefix with an explicit truncation marker and fail the task instead of allowing dependent decisions to consume silently truncated successful output. Preserve ordinary runtime failure reason and nonzero-exit semantics; do not invent an exit code when the provider exposes none. Raw diagnostic log retention remains the existing runtime behavior.

Expose custom task identity/revision/name, prepared inputs and source summary in task history using the persisted execution snapshot. A dedicated output panel displays TaskRun.Output. Existing versions and retries remain intelligible after catalog deletion. A later Decision may consume a dominating ordinary Custom task's output through the existing exact-node source rules. No automatic copying to PlanArtifact is performed.

## Graph and callback integration

Custom tasks are ordinary sequential AI nodes and may appear in existing Loop bodies. Each iteration retains existing task-run uniqueness. They remain forbidden in Parallel branches, which are explicitly Plan-only; adding a generic mapping must not accidentally broaden that rule. Decision dominator analysis may treat Custom as an ordinary task, while retaining rejection of Loop/Parallel body references. Reject malformed custom settings in every schema path; preserve v1alpha1-3 compatibility and exact built-in mappings.

Audit every mapping using TaskRunKind, WorkflowStep or task type, including retry helpers, transition helpers, normalization, node adapters, filters and status styles. Existing queued Custom workflows must enter the generic path directly rather than falling into the Plan-ready gate. CurrentDefinitionStepId is required for new generic execution; never recover a Custom cursor by selecting the first/latest task of that kind.

Fix worker callback correlation as part of generic-task support. WorkerAgentMessageService and WorkerAgentAuthRefreshService currently fetch the latest TaskRun by kind; the message path also accepts a callback when that run has no external ID. Replace this with exact WorkflowId + parsed/defined TaskRunKind + assigned ExternalId lookup. Never attach a late callback to another Custom node or loop iteration, and never fall back to latest kind. Custom streaming callbacks are log-only: record bounded diagnostic messages against the exact task, but never read/append/upsert TaskRun.Output or task status from that path. Final Custom output and terminal status are written exclusively by authoritative runtime result polling. This prevents late same-attempt callbacks or a callback/completion race from replacing terminal output or reviving Running state. Preserve existing built-in streaming behavior. Callbacks arriving before assignment are rejected safely; authoritative final output still comes from runtime result polling. Preserve authentication-setup/model-discovery callback special cases. Test late/stale/unknown callbacks, repeated Custom task kinds, terminal callbacks and a deterministic concurrent callback/completion race; assert that final output and status remain unchanged. Broader callback protocol redesign is unnecessary for this release.
