# Issue #14: customizable agent personas (0.14.0)

Status: independently reviewed plan, approved for implementation after #11 deploys. Actual issue criteria: selectable step personas, operator-visible/editable persona configuration, and persona-specific prompt context. No new execution types, permissions, model discovery behavior, or infrastructure changes are required.

## Catalog and API

Add an operator-managed Persona catalog with string Id, Name, Instructions, Tone, OperatingConstraints, integer Revision, IsDeleted, CreatedAt, and UpdatedAt. IDs are server-generated and immutable; labels need not be unique. Seed/present a built-in `default` persona at revision 1 with no added prompt context. It cannot be edited or deleted and preserves current behavior byte-for-byte. User-created personas start at revision 1; every successful edit increments Revision once.

Expose GET /api/personas and GET /api/personas/{id} under WorkflowView. List returns active personas including default. Expose POST /api/personas, PUT /api/personas/{id}, and DELETE /api/personas/{id} under ManagementAdmin, matching workflow-definition management. PUT includes expectedRevision; DELETE includes expectedRevision as a query parameter. Use optimistic concurrency so stale edits/deletes return 409 and cannot silently overwrite another operator. Return 404 for unknown/deleted IDs. Deletion marks the catalog row deleted; it never deletes immutable version snapshots. API responses contain Id, fields, Revision, builtIn flag, and timestamps; no mutable builtin flag supplied by clients.

Validate trimmed nonempty name (max 120 characters), instructions (max 16000), tone (max 1000), and operating constraints (max 8000). Empty context fields are valid. Treat all fields as plain text: no template interpolation, executable expressions, shell commands, or model/settings overrides. Catalog configuration does not grant tools or permissions. Add EF mappings, fake-store parity and a generated migration for persona rows; no existing definition rewrite or backfill is needed. Keep catalog operations scoped independently of workflow orchestration.

## Selection and immutable snapshots

Add optional `defaultPersonaId` to WorkflowDefinitionDocument and optional `personaId` to WorkflowDefinitionStep. Workflow default null means built-in default. An AI task's null personaId inherits the workflow default; explicit `default` overrides a custom workflow default with unchanged built-in behavior. Allow selection only on Plan, Implement, and AddressComments (including Plan tasks in parallel branches). Direct CreatePullRequest and all control nodes cannot select a persona and never receive persona prompt context. Workflow default may remain configured even when a workflow currently has no AI tasks.

Add an optional server-resolved `personaSnapshot` on each AI task, containing Id, Revision, Name, Instructions, Tone and OperatingConstraints. Snapshot every eligible task at version creation after resolving inheritance. Resolve each distinct catalog ID once per save so every use of the same persona receives one coherent revision. Ignore/replace any client-supplied snapshots; a client cannot turn arbitrary snapshot JSON into an authoritative catalog revision. Preserve node IDs, graph settings and editor metadata while enriching the document.

Saving a new version deliberately captures the selected catalog persona's current revision. Existing versions/runs always use their stored snapshot and never reread the catalog at execution. Catalog changes or deletion cannot alter pinned versions, restarts, or retries. Opening an older version shows its saved persona revision. If the active catalog revision differs, show the concrete note `Saved version uses revision X; Save Version will use revision Y` before saving. New versions cannot select a deleted persona; the editor retains the missing selection visibly until it is replaced. A pinned older version with a deleted catalog reference remains executable from its snapshot.

Disabled incomplete versions remain savable: retain unresolved IDs and show node/workflow validation errors, snapshot other resolvable AI tasks, and leave unresolved snapshots absent. Enabled saves reject unknown/deleted IDs or inappropriate node overrides. The nonpersisting validation endpoint checks current selected catalog references and returns node references. Runtime validation checks the pinned snapshot contract only, never current catalog availability. Legacy documents with neither persona references nor snapshots use default unchanged; explicit non-default references without a usable snapshot must not silently fall back during execution. Existing EnsureDefaultWorkflowDefinition/bootstrap behavior remains unchanged and does not require catalog access.

## Prompt composition and runtime integration

Introduce a small application-owned pure PersonaPromptComposer. Built-in default adds nothing, preserving the exact existing prompt. Custom personas add one clearly labeled plain-text section with their instructions, optional tone and operating constraints; the existing task prompt remains intact. Do not substitute the persona for task instructions and do not interpret persona content as a template.

Extract common agent-task preparation from the existing StartAgentTaskAsync settings resolution so both sequential launches and the parallel direct-launch path call it. Preparation resolves the pinned task snapshot, composes the prompt once, and returns the prepared AgentTask plus persona identity for audit. Keep parallel launch uncertainty and durable ExecutionAttemptId semantics intact; do not route parallel tasks through the existing failure-handling wrapper that would mark uncertain starts failed. Read the persona using DefinitionStepId, never TaskRunKind or current global Parallel cursor. Preserve model/AI inheritance and CLI-discovered model selection.

Record persona ID, revision, and name in task-start/settings-resolved events for sequential and parallel AI jobs. Runtime/history reads use the immutable task snapshot; they must remain intelligible after catalog deletion. Personas have no effect on direct provider CreatePullRequest operations, triggers, loops, parallel barriers, decisions, label gates, or source-control authorization. Fresh task rendering before each retry prevents duplicate persona sections; retries reuse the same pinned persona revision.

## UI and editor

Add a Personas page using the current page/panel/form design language. Workflow viewers can browse and inspect; management admins can create, edit and delete. Use a compact searchable list, selected-persona editor, visible revision/built-in status, ordinary validation messages and a Cancel/Delete confirmation. Preserve unsaved form edits on failed saves and show a conflict rather than silently replacing them after a 409. A deletion confirmation explains only the real effect: future selection is unavailable, existing workflow versions retain their snapshot.

In workflow settings add a workflow-default persona selector with preview. In the AI task inspector add `Inherit workflow persona`, `Default behavior`, and active custom personas with concise name/revision information and a readable context preview. Hide the selector on CreatePullRequest/control nodes and clear inappropriate task overrides when changing an AI task to a non-AI type. Update graph adapters and editor state so references survive save/reload, duplication, undo/redo, version switching and legacy normalization. Server snapshot fields are read-only metadata, not editable inputs. Selecting a different persona updates the preview from the catalog while showing the effective save revision clearly.

## Acceptance and verification

Add catalog tests for CRUD, bounds, immutable default, revision conflicts, delete semantics, and ManagementAdmin/WorkflowView permissions. Add real PostgreSQL migration and optimistic-concurrency tests. Add definition tests for workflow inheritance, explicit step override/default opt-out, invalid control/CreatePullRequest override, missing/deleted reference, disabled unresolved drafts, consistent revision reuse, ignoring supplied snapshots and metadata/layout preservation.

Prove immutable behavior by saving version A, editing/deleting its persona, then running/resuming/retrying A with its original content; saving version B with an active edited persona captures the new revision. Prove malformed explicit snapshots fail rather than fall back, while untouched legacy documents preserve prompt parity. Test both sequential and parallel preparation: Plan, Implement, AddressComments get exactly one persona section; direct CreatePullRequest gets none; per-step AI/model overrides and durable attempts remain unchanged.

Browser tests cover catalog create/edit/conflict/delete, read-only inspection, workflow default, per-step override/inheritance/default opt-out, saved-version versus current revision preview, unknown/deleted selection handling, disabled save/reload, node-type change, undo/redo and failed-save retention. Inspect desktop/narrow screenshots and ensure all existing node types still render/move.

Obtain independent implementation review, then run targeted/full backend, frontend build and browser smoke, managed development harness, and required migration/startup Kubernetes E2E. Align version files/docs once to 0.14.0. Commit main, push, wait for a healthy deployment, then close #14 with solution, snapshot semantics, test counts and deployed version.
