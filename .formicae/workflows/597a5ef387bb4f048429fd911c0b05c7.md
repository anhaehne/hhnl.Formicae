## Changes from previous plan

- Replaces the obsolete Plan-mode blocker with a complete, repository-grounded implementation plan.
- Accounts for the current hard-coded sequential orchestrator and the `TaskRun` uniqueness constraint, both of which must change before steps can repeat.
- Includes DSL/editor support, persisted iteration history, deterministic guardrails, migrations, and focused tests.

## Implementation plan

1. Define a backward-compatible loop DSL.

   - Add a new schema constant such as `formicae.workflow/v1alpha2` in `DefaultWorkflowDefinitions.cs`, while continuing to deserialize and execute existing `v1alpha1` definitions.
   - Extend `WorkflowDefinitionDocument` in `WorkflowModels.cs` with loop definitions containing:
     - Stable loop ID.
     - Ordered body step IDs, allowing one step or a contiguous group.
     - Required repeat count.
     - Required `maxIterations`.
     - Optional timeout in seconds.
     - Exit step ID.
   - Keep termination deterministic: execute the body exactly `repeatCount` times; fail before another iteration when `maxIterations` or timeout would be exceeded.
   - Document and validate whether elapsed timeout uses the persisted loop start timestamp and injected `IClock`, so restarts produce the same outcome.

2. Extend workflow-definition validation.

   - Update `WorkflowDefinitionValidator.cs` to accept both schema versions and validate loop IDs, positive bounds, `repeatCount <= maxIterations`, positive timeouts, known/reachable body and exit steps, non-overlapping loop ownership, and valid transitions.
   - Replace the blanket cycle rejection with loop-aware graph validation: back-edges are legal only inside declared loop bodies; undeclared cycles and disconnected nodes remain errors.
   - Add focused cases to `WorkflowDefinitionTests.cs` for a valid single-step loop, valid grouped loop, invalid bounds, invalid references, and undeclared cycles.
   - Update the default definition tests to confirm the existing MVP workflow remains unchanged and valid.

3. Persist execution position and iteration history.

   - Add stable execution fields to `Workflow`, including the current definition step ID.
   - Extend `TaskRun` with definition step ID and loop iteration number; remove the current uniqueness assumption on `(WorkflowId, Kind)` so repeated executions create distinct runs.
   - Introduce a persisted `WorkflowLoopIteration` record containing workflow ID, loop ID, iteration number, start/completion timestamps, outcome, and failure reason.
   - Add the corresponding store operations to `IWorkflowStore`, `EfWorkflowStore`, and `InMemoryWorkflowStore`.
   - Configure entities and indexes in `FormicaeDbContext.cs`, then generate an EF migration following `agent-os/standards/database/ef-migrations.md`. Preserve existing run data with sensible defaults and replace the task-run unique index with an index suitable for step/iteration lookup.

4. Make orchestration definition-driven.

   - Refactor `WorkflowOrchestrator.cs` so the persisted current step ID and the selected immutable definition version determine which built-in task runs next, instead of the fixed `WorkflowStatus` switch and `ExpectedNextKind`.
   - Retain current statuses as broad observability states by mapping each built-in task kind to its existing status/`WorkflowStep`.
   - Resolve loop entry, body progression, repeat, and exit through a small execution-cursor component or helper that can be unit-tested independently.
   - Create a new `TaskRun` for every step execution, identified by step ID and iteration; update reuse/polling queries to address the active execution rather than one run per `TaskRunKind`.
   - On each loop entry, persist an iteration record before executing its body; mark it succeeded on body completion and advance either to the next iteration or exit step.
   - Before starting each iteration, compare its number and elapsed duration with the persisted guardrails. On violation, transition the workflow to `Failed` with a stable failure code/message and emit a structured `WorkflowEvent`.
   - Ensure retries and process restarts resume the same active iteration without duplicating successful task runs or advancing the counter twice.

5. Expose loop state through management APIs.

   - Extend workflow detail/task-run response models and `WorkflowMapping.cs` with step ID and iteration metadata.
   - Include ordered loop iteration history in the existing workflow-detail response assembled by `WorkflowService.cs` and exposed from `Program.cs`.
   - Keep summary endpoints compact; expose guardrail failures through the existing `FailureReason` and event mechanisms.

6. Add workflow-editor support.

   - Update the TypeScript definition types in `ClientApp/src/api.ts`.
   - Extend `workflowGraph.ts` to round-trip loop metadata without losing it when definitions are opened and saved.
   - Add loop configuration controls to `WorkflowDefinitionsPage.tsx`: body steps, repeat count, maximum iterations, optional timeout, and exit step.
   - Mirror key server validation client-side and render declared loop edges/groups distinctly enough to distinguish them from invalid arbitrary cycles.
   - Extend `ClientApp/tests/e2e/smoke.spec.ts` to create or edit a loop definition, save it, reload it, and verify its settings persist.

7. Add orchestration acceptance tests.

   - In `WorkflowOrchestratorTests.cs`, add a successful bounded-loop test proving:
     - A step or multi-step body runs the configured number of times.
     - Each execution has a distinct `TaskRun`.
     - Iteration history is ordered and complete.
     - The workflow exits the loop and reaches completion.
   - Add a guardrail test using the fake clock that exceeds the timeout (or persisted max-iteration state), then assert deterministic failure status, reason, event details, and no extra agent execution.
   - Add a restart/idempotency test that reconstructs the orchestrator mid-loop and confirms the current iteration resumes without duplication.
   - Update existing task-run assertions and test doubles for multiple runs of the same kind.

8. Version and verify the change.

   - Apply one minor version bump across `Directory.Build.props`, `deploy/helm/formicae/Chart.yaml`, `deploy/helm/formicae/values.yaml`, and applicable release/deployment documentation.
   - Run:
     - `dotnet test tests/hhnl.Formicae.Tests/hhnl.Formicae.Tests.csproj`
     - `npm test` or the available frontend validation scripts from `src/hhnl.Formicae.Api/ClientApp`
     - `npm run test:smoke` from that directory
     - The repository’s fast verification command after `./scripts/formicae-dev.sh prepare`
     - `./scripts/run-k8s-e2e.sh`, because the change includes an EF migration and startup-sensitive persistence changes.
   - Manually verify through the running UI that a loop definition can be saved, selected for a workflow, observed across iterations, and diagnosed after a guardrail failure.
   - In the pull-request summary, report the exact commands and outcomes plus the number of tests added, removed, and edited.
