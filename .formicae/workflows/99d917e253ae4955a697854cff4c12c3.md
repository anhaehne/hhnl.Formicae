## Implementation plan

Extend existing custom tasks with named, typed outputs and explicit output-to-input bindings. Typed scalar inputs, immutable task snapshots, prepared execution context, and free-text output already exist.

**Scope:** Support `string`, `number`, and `boolean` parameters. Preserve existing tasks and workflows unchanged when outputs and bindings are absent. Data connections must follow existing execution order; they do not schedule tasks.

### 1. Record the contract and execution rules

Save lightweight documentation under `agent-os/specs/<timestamp>-task-data-passing/`.

Define:

- Output definitions: name, scalar type, and required flag.
- Input bindings: consumer input name → producer workflow step ID and output name.
- An input may have a literal value or a binding, never both.
- Producers must be guaranteed to execute before consumers. Reject self-references, downstream references, and references to conditionally skipped producers.
- Within one loop body, resolve outputs from the same iteration. Allow producers outside the loop that execute before entry; initially reject bindings leaving loop bodies or crossing loops.
- Keep current parallel-region restrictions; do not expand parallel custom-task execution in this issue.

### 2. Extend contracts, persistence, and validation

Update `CustomTaskModels.cs`, `CustomTaskService.cs`, and `CustomTaskDefinitions.cs` under `src/hhnl.Formicae.Application/Workflows/`.

- Add output schemas to catalog requests, responses, and `CustomTaskSnapshot`.
- Add optional bindings to `WorkflowCustomTaskSettings`, retaining the existing literal `Inputs` dictionary.
- Add structured output storage to `TaskRun` in `WorkflowModels.cs`; retain `Output` for existing history behavior.
- Update `EfCustomTaskStore`, workflow persistence, in-memory stores, `FormicaeDbContext`, and response mapping.
- Default missing output schemas to empty for older catalog entries and pinned snapshots.
- Reuse existing scalar validation and limits. Validate unique names, declared parameters, matching types, binding/literal conflicts, and execution-order rules after task snapshots are resolved.
- Generate the EF migration using `dotnet ef migrations add`; follow `agent-os/standards/database/ef-migrations.md`.

**Tests:** Extend catalog, API, definition, migration, and persistence coverage for compatibility and invalid schemas/bindings.

### 3. Capture validated outputs on completion

Extend `WorkflowOrchestrator.Custom.cs` and the agent result extraction path.

- For tasks declaring outputs, append a deterministic instruction requiring the final response to be a JSON object containing named output values.
- Supply the pinned output schema in the task context.
- Use `System.Text.Json` to parse the final response strictly; reject duplicate/unknown names, missing required outputs, invalid types, and oversized values.
- Persist validated outputs together with successful task completion, before advancing the cursor. Invalid output fails the task with an actionable error.
- Tasks without output schemas retain current free-text behavior.
- `OpenHandsAgentRunner.ExtractAgentOutput` currently recognizes Codex final-message events. Add custom-task-specific final-response extraction for both supported CLI paths; do not parse arbitrary logs as parameter values.
- Preserve `WorkerAgentMessageService`’s rule that streaming callbacks cannot overwrite authoritative completion.

**Tests:** Cover valid output, malformed JSON, schema violations, both CLI event formats, failed execution, and late callbacks.

### 4. Resolve and freeze bound inputs

Extend preparation in `CustomTaskDefinitions.cs` and `WorkflowOrchestrator.Custom.cs`.

- Resolve producer runs by workflow ID, definition step ID, and applicable loop iteration using persisted execution state.
- Require a successful producer with validated structured outputs.
- For a missing optional output, apply the consumer input’s default/required rules. A configured binding must never silently become a literal.
- Record resolved values and producer run/attempt identity in `PreparedCustomTaskExecution`.
- Persist preparation before starting external execution, as the orchestrator already does.
- Update `ValidatePrepared` to validate frozen bound inputs and provenance against the pinned definition.
- Preserve prepared inputs on retry/restart. Clear structured outputs when retrying a producer in `WorkflowService.RetryTaskRunAsync`.

**Tests:** Run producer → consumer workflows through completion, restart, and retry; verify iteration isolation and failure before launch when source data is unavailable.

### 5. Add parameter editing and connections

Update `ClientApp/src/api.ts`, `CustomTasksPage.tsx`, and `workflowEditor/CustomTaskSchema.tsx`.

- Add output-schema editing using the existing input-schema patterns.
- In `CustomTaskSettings.tsx`, offer literal/default or producer-output selection for each input.
- Show only eligible producers and matching output types; retain visible errors for stale bindings after task revisions or graph edits.
- Add named parameter handles and distinct data edges in `workflowEditor/Node.tsx` and `workflowGraph.ts`. Reuse installed React Flow’s [named handles](https://reactflow.dev/learn/customization/handles).
- Serialize data connections into bindings. Keep them separate from control edges when deriving `nextStepId`, validating execution order, and calculating layout.
- Ensure connection changes participate in undo/redo, save/reload, and node deletion.
- Expose structured outputs and resolved input provenance in task history.

**Tests:** Extend `WorkflowEditorTests.cs` and `tests/e2e/customTasks.spec.ts` for schema editing, connection creation/removal, undo/redo, round-trip persistence, validation errors, and execution history.

### 6. Verify and document

Update the roadmap and release documentation, applying one minor version bump across the aligned version files. Report exact verification outcomes and tests added/removed/edited.

**Acceptance:** A saved workflow passes a validated named output between custom tasks, survives restart and retry with frozen inputs, rejects invalid connections, and continues running existing workflows without modification.
